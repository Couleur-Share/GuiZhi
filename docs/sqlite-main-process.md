# SQLite 要不要移出主进程

结论先说：**不移。** 实测下来主进程被数据库阻塞的时间远小于此前的估计，
而剩下的两处长阻塞各有比「换架构」便宜得多的解法。这份文档记下数据和推理，
免得下次又凭印象重开这个话题。

## 数据怎么来的

`scripts/bench-sqlite-block.ts`，可复跑：

```bash
pnpm exec tsx scripts/bench-sqlite-block.ts
```

条目正文固定 2000 字，每条 3 个 1024 维向量块，覆盖 1k / 5k / 20k 三档。
20k 条对应 364MB 的库——按个人知识库的增长速度，这是好几年的量，
可以当作现实上界看。下面的数字都取自 20k 档（Windows 11 / NVMe）。

## 优化前后

| 操作 | 优化前 | 现在 |
| --- | --- | --- |
| 列表首屏（50 条 + 标签） | 281 ms | 16 ms |
| 列表翻到第 20 页 | 147 ms | 14 ms |
| 全文搜索 | 5 ms | 5 ms |
| 单条读取 / 保存 | 4 / 15 ms | 4 / 15 ms |
| 语义检索（全量余弦 top-10） | 15106 ms | 1448 ms |
| 备份 VACUUM INTO | 1620 ms | 1590 ms |
| 启动完整性检查 | 920 ms | 0 ms（正常退出后跳过） |

三处改动换来的：

1. **语义检索的分批翻页从 `LIMIT/OFFSET` 改成 rowid 游标。** OFFSET 要求
   SQLite 先扫过并丢弃前 N 行连接结果，分批遍历全表就成了平方级——
   120 个批次累计丢弃约 360 万行。批处理本来是为了不阻塞主线程，
   结果把总耗时放大了十倍。
2. **`(deleted_at, status)` 覆盖索引 + 启动时 ANALYZE。** 列表每次都要数总数，
   而单列的 `idx_items_deleted` 定位到行之后还得回表读 `status`；条目表每行
   带 2KB 正文，两万次回表就是两万次大页读。并进索引后 COUNT 全程走索引。
   ANALYZE 则修正了另一半：没有统计信息时规划器把 `deleted_at IS NULL`
   当成等值约束、估成高选择度，于是挑中它再对全部匹配行建临时 B 树排序；
   有了统计信息才改走 `idx_items_pinned_updated` 顺序扫描并在 LIMIT 处收工。
3. **启动完整性检查只在上次非正常退出后才跑。** 正常退出会留下标记文件，
   SQLite 的事务保证此时文件自洽。标记超过一周仍强制查一次。

## 那还剩什么在阻塞主进程

只有两项，且都不是「随便点点就会撞上」的操作：

- **备份 VACUUM INTO，1.59 秒。** 定时自动备份或手动触发。现在会先弹提示，
  用户知道界面为什么顿住。
- **语义检索，总计 1.45 秒。** 但它分 120 批、批间让出事件循环，
  单批只占用约 20 毫秒，不构成一次长阻塞——界面全程可响应，
  只是问答要等一秒多才出结果。

其余所有操作都在 20 毫秒以内。**日常打字、翻列表、搜索、保存，主进程根本没被卡住。**

## 移出主进程要付什么代价

- 每一个 DAO 调用点都要从同步改成异步。`packages/db` 下的类方法目前全是同步返回，
  调用方遍布 `main/ipc`、`main/services` 与迁移脚本。
- 结果要跨 IPC 序列化。列表查询已经用 `substr` 裁过正文了，但向量 BLOB、
  Wiki 正文这类大对象要多一次结构化克隆的拷贝。
- 失去同步事务。`db.transaction(() => {...})` 这种写法在跨进程后必须重新设计，
  否则事务边界会被异步调用切开。
- `node-sqlite3-wasm` 是 Emscripten 构建，在 utility process 里要重新验证
  文件锁与 VFS 行为。它连 WAL 都不支持（实测执行 `PRAGMA journal_mode = WAL`
  既不报错也不生效），跨进程的假设不能照搬原生 SQLite 的文档。

换来的收益是：备份那 1.59 秒不再冻界面。就这一项。

## 所以真要动，先动什么

按收益排序，都比搬家便宜：

1. **备份放进 utility process。** 只需要一个只读连接跑 `VACUUM INTO`，
   不涉及现有 DAO 的任何改写——这是「把一个函数搬走」，不是「把数据层搬走」。
2. **语义检索的 1.45 秒里约四分之三花在加载上**（120 批 × 约 9 毫秒），
   而不是余弦计算。6 万个 1024 维 Float32 向量 = 240MB 要跨 wasm 边界搬进 JS。
   降这一项的办法依次是：向量量化到 int8（数据量降到四分之一）、
   ANN 索引（只加载候选）、或改用 sqlite-vec 让打分留在 SQL 里。
   注意这三条都和「SQLite 在哪个进程」无关。
3. 真到了需要跨进程的规模，那时的正确做法多半是换掉 `node-sqlite3-wasm`
   而不是给它套一层进程——原生 better-sqlite3 能开 WAL，读写不再互斥，
   收益比搬进程大。当初选 wasm 是因为原生模块在 Windows ARM64 上构建不过，
   这个前提值得重新核实。
