# 分享入口 spike（仅 dev 包）

**状态**：探针的源码、隔离测试与编译已完成；**真机结论尚未取得**。取得结论需要两件只有你能做的事：给 dev 包配置调试签名（见 [device-loop.md](device-loop.md)），以及从几个 App 各分享一次。结论出来之前，不投入 RDB 迁移与 ShareExtension（计划阶段 5 的 5a / 5b）。

## 为什么先做 spike

“分享到归知”若走系统分享面板，需要一个 `ShareExtensionAbility`；它可能与主应用在不同进程里同时运行，而 `Preferences` 明确不支持多进程，所以要先把草稿与编辑器存储迁到 RelationalStore。两步合计约 4.5–6.5 天，前提是下面这些事实成立，而它们现在都是假设：

- 第三方（且是调试签名的）ShareExtension 会出现在浏览器、微信、小红书、抖音的分享面板里；
- 各来源交给扩展的记录含哪些字段（标题、描述、文字加图片混合……）；
- 扩展在不在独立进程；
- 扩展里能不能读 Asset Store 里的配对凭证、能不能访问网络。

spike 只花不到一天，先证伪再投入。

## 装了什么（只在 dev 包里）

| 组成 | 作用 |
| --- | --- |
| `ShareDiagExtAbility`（`type: share`） | 接收 `general.text`、`general.image`、`general.object`（最多 9 条）。收到分享后：把每条记录整理成“形状”落盘；在**当前进程**实测 Asset Store、配对凭证读取、访问中转；面板上给出摘要。**不保存分享正文，也不向中转投递任何内容** |
| `ShareDiagPanel` | 分享面板里的摘要页：来源、每条记录的字段长度、现有逻辑会如何处理、三项探测结果；按钮「复制报告」「完整报告页」「关闭」 |
| `ShareDiagAbility` + `ShareDiagReport` | 完整报告页：打开时先在**主进程**里记一条基线（同样的三项探测，并记录进程号），再展示汇总报告；按钮「复制诊断报告」「刷新」「清空」 |

扩展与报告页通过 `entry/hvigorfile.ts` 的构建插件，仅在 `dev` 产品里注册进 `module.json5`（`src/dev/module.json5` 不会被合并，已实测）；`pages` 路由表由 dev 资源目录覆盖。正式包不含这些：`inspect-hap.ps1 -ForbidExtensions -ForbidCode 'ShareDiag','sharediag'` 与 `tests/share-spike-isolation.test.cjs` 都会检查，源码里未被引用的 `sharediag` 目录也不会被编进正式包。

## 怎么跑（需要你操作）

前提：dev 包已按 [device-loop.md](device-loop.md) 完成调试签名并能安装，且在 Dev 包里**完成配对**（否则凭证一项只能得到“未配对”，结论是证据不足）。

1. 构建并安装 dev 包（覆盖安装）：`build.ps1 -Product dev -Isolated -Build`，再 `device.ps1 install`。
2. 记下**主进程基线**，并让归知收集 Dev 在整个测试期间保持在后台（不要从多任务里划掉），否则扩展与主进程的进程号没有可比性：
   - 有命令行回路：`device.ps1 launch -Ability ShareDiagAbility` 打开报告页；
   - 没有：先正常打开一次归知收集 Dev，然后分享一次，在扩展面板里点「完整报告页」——它运行在主进程里，同样会记下基线。
3. 依次从**浏览器、微信、小红书、抖音**各分享一次，分享面板里选「归知收集 Dev」。每个来源建议分享两种内容：一条纯链接或纯文字，以及一条带图片的内容（例如小红书笔记、微信公众号文章）。**没有出现在分享面板里**这件事没有任何日志能记录，请在文末的结果表里手动写。
4. 每次分享后面板上会显示摘要；全部分享完，回到报告页点「刷新」，再点「复制诊断报告」发给我。也可以用 `device.ps1 dump` 读取报告页文字（长文本是否会被截断尚未验证）。
5. 结束后点「清空」或卸载 dev 包；正式包和它的数据不受影响。

分享内容不会进入你的桌面收件箱，所以不需要 `[dev-test]` 前缀。扩展会读到分享的内容，但只记录长度与类型（见下文“隐私与安全边界”）；即便如此，也请避开含敏感信息的页面。

## 报告怎么读

| 要回答的问题 | 报告位置 | 怎么判 |
| --- | --- | --- |
| 归知 Dev 是否出现在各来源的分享面板 | 人工 | 只能由你观察；报告里有该来源的记录，说明它至少被选中过一次 |
| 各来源的记录形态 | 「来源明细」 | 每个来源一段：`字段出现：content · title · description · uri · 缩略图` 是出现该字段的**记录条数**；`类型` 是各记录的 UTD；`现有逻辑会：…` 是用现在的 `pickShareText` 与 `parseCapture` 预测的处理结果（能不能整段当文字、忽略了几条、识别为链接还是文字、拆成几个条目）。文字加图片的混合会体现在“类型”与“忽略”里 |
| 扩展是否独立进程 | 「扩展进程」 | `独立进程（扩展 pid … 主进程基线 pid …）` 或 `与主进程相同`；没有基线会提示先开一次报告页 |
| 扩展内 Asset Store 与网络是否可用 | 「最近一次分享」与「主进程对照」 | 三项各为 正常 / 无数据 / 失败 / 跳过 / 未完成：Asset Store 读写（用自己的探测条目，不碰真实凭证）、读取真实配对凭证、访问中转（已配对时调用只读的 `GET /v1/session`，未配对时改测 `https://example.com/`）。与「主进程对照」逐项比较，就能判断差异是扩展环境造成的还是本来就有 |
| 调试签名的包是否被列出 | 人工 | 与第一项相同：四个来源都不出现，才怀疑签名类型；先用 `hdc shell bm dump -n com.couleurapp.guizhi.capture.dev` 确认已安装包里确有 `ShareDiagExtAbility`（该命令未在本机验证） |

## 判据

判据沿用计划：**出现且扩展内凭证与网络可用则 go，否则 no-go**。报告的「结论」只判断技术侧，且只看两件事——扩展内能否读取配对凭证、能否访问中转；Asset Store 读写只写成“参考”，因为扩展只读凭证，写入发生在主应用里。

| 报告结论 | 含义 | 处理 |
| --- | --- | --- |
| 技术侧可行 | 最近一次分享中，读取凭证与访问中转都成功 | 再看人工那一项：至少你要的来源里能看到归知 Dev，才是 **go** |
| 技术侧受阻 | 凭证读取或网络已确认失败，原因逐条列出 | **no-go** |
| 证据不足 | 没有分享记录、未配对、缺少主进程基线或探测未完成 | 补测，不下结论 |

“部分可用”（例如只有浏览器里出现）按计划走 no-go 分支；如果你认为只覆盖部分来源也值得做 ShareExtension，可以明确选择 go，那是产品取舍，不由报告替你决定。

## 对下一步的影响（p5-build）

- **go**：先做 5a（`SqlPort` 加 RelationalStore 实现，一个事务内从 Preferences 迁入并校验条数，保留旧数据两个版本，失败可重试并允许复制旧草稿文本），再做 5b（`ShareExtAbility` 与 `ShareSheet`：预览、识别行、模式、存入/发送，本地落盘先于网络，主应用回前台时重载草稿）。若报告显示扩展**与主进程相同**，5a 的必要性需要重新评估——但这次只在主应用存活时测过，冷启动时扩展会另起进程，评估前要补测。
- **no-go / 部分可用**：做“分享后自动返回来源 App”（`moveAbilityToBackground`，设置项，默认开，回退目标需真机确认），并复用阶段 2 的自动发送。不做 RDB 迁移。

## 隐私与安全边界

| 会记录 | 绝不记录 |
| --- | --- |
| 每条记录的 UTD、`content` / `title` / `description` / `uri` 的**长度**、缩略图字节数与地址长度、`uri` 的协议类别 | 分享的正文、标题、描述、链接、缩略图地址 |
| 来源包名、`want` 参数的**名称**（仅由安全字符组成的前 30 个）、启动原因 | `want` 参数的值（来源包名除外） |
| 三项探测的状态、错误码、耗时；机型、系统版本、归知版本；进程号 | 凭证、中转地址、口令 |

- 文件为应用沙箱内的 `share-probe.jsonl`，最多保留 60 条，写入用“临时文件 + 重命名”；`.tmp` 残留不影响读取。
- Asset Store 探测只写入、读回、删除自己的条目 `guizhi.spike.probe.v1`；真实凭证只判断“读到没有”，不输出内容。
- 报告只含以上字段，可以直接发给我；不含任何可还原正文的信息。

## 已知限制

- 只回答“出现与否、字段形态、进程、Asset Store 与网络”；扩展面板被划走后进程还能活多久、系统对扩展的时间和内存限制，属于 5b 之前才要补测的内容。
- 字段形态只代表**这个版本的来源 App**；来源 App 更新后可能变化，因此结果表要记录日期和 App 版本。
- 进程对比依赖主进程基线；基线取自报告页，所以第一次分享前请先打开一次报告页。
- 调试签名与正式签名的包在分享面板里的可见性可能不同；本 spike 使用调试签名的 dev 包，结论不自动等于正式包。
